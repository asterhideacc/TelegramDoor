# 设计说明

## 运行结构

同一个 Worker 托管静态后台、验证页面、管理 API 和 Telegram Webhook。D1 保存状态，Cron 清理过期数据。没有常驻服务器、Redis、共享 Bot Token 或外部 AI 服务。

```text
Telegram 私聊 → /webhook → 验证 / 限频 / 过滤 → Telegram copyMessage
                    ↕                              ↕
                   D1 ← 消息对应关系 ← 管理员引用回复 / 表情按钮
                    ↕
浏览器 → 登录 → /api/admin/* → 统计 / 记录 / 设置 / 管理
访客验证页 → Turnstile → /api/challenge/verify → D1 验证状态
```

## 消息身份

只接受 `chat.type = private` 且 `chat.id = from.id` 的普通用户消息。管理员必须同时满足聊天 ID 与发送者 ID 等于 `OWNER_ID`。绝不依赖显示名、用户名、转发来源文字或消息正文中的用户 ID 来授权。

`message_links` 同时保存源聊天/消息和目标聊天/消息；源和目标都有联合唯一约束。引用消息时查找该映射，确定对方聊天，未知映射不会猜测收件人。回复引用也使用对应的对方消息 ID。不同用户间的引用不会交叉。

每条转发消息下方有明确用户身份（仅管理员可见）、回应按钮与封禁入口。回调回应验证操作者、聊天 ID、消息 ID 和映射；封禁后旧回应按钮也不能发送回应。

后台回复先创建管理员聊天镜像，再复制给访客并建立映射。管理员镜像存在本身不代表访客已收到；复制失败会在后台记录为失败。

## 投递和错误

Webhook 处理在返回 HTTP 200 之前完成，不把关键消息发送丢入无持久化保证的后台异步任务。`updates` 使用 SQL 原子领取及 120 秒租约，成功更新返回 200；正在处理的重复更新返回 503，已完成的重复更新返回 200。已建立的源消息映射防止常见重复复制。

网络故障、Telegram 5xx、429 返回 503 让 Telegram 重试；429 附带 `Retry-After`。确定的 4xx 复制失败记录下来并适当通知发送者，不无限重试。回调确认失败不会重复执行已完成的管理操作。

外部 Telegram 发送与 D1 写入不是同一事务，不能提供严格恰好一次语义。保留这个边界比声称永不重复更诚实；未来可加入带人工重试的持久化发件箱，但依然无法消除外部接口的模糊成功窗口。

## 验证与过滤

默认：30 天验证有效期、每用户每分钟 10 条消息（包含命令和编辑）、验证码 5 分钟有效、连续 3 次失败冷却 15 分钟。算术题是低门槛保护，不抵抗有针对性的脚本。

规则优先级：封禁 → 限频 → 暂停接收 → 白名单 → 验证冷却/有效期 → 链接/关键词过滤。白名单仍受封禁、限频与暂停影响。编辑消息同样过滤，拒绝的编辑不会覆盖已经送达的正常版本。

Turnstile Secret 以 AES-GCM 加密存入 D1，密钥通过 Bot Token 的 HMAC 派生。绑定 `hostname`、`action=telegramdoor` 与 `cdata=challengeId`。挑战通过条件 DELETE 一次性消费，并且只对未封禁、未冷却用户设置验证有效期。修改验证方式会使旧方式的挑战无法继续使用。

Turnstile 服务端密钥配置错误和服务端故障不消耗用户验证次数。密钥错误/过期与网络失败必须在真实部署中实测。

## 登录和部署

三个用户提供的配置：`ADMIN_PASSWORD`、`BOT_TOKEN`、`OWNER_ID`。Webhook Secret 独立 HMAC 派生，无需第四个用户配置。Worker 同源托管 UI，前端不持有 Telegram 或 Cloudflare 凭据。

一键部署向导复制源码、创建 D1 资源，并将模板里的全零 `database_id` 占位值替换成部署者账户的真实 ID；无需用户提前 Fork。分步备用方案则手工创建并填写绑定。部署脚本只构建与发布，不依赖构建令牌的 D1 迁移接口权限。第一次 API/健康检查请求或定时清理，通过 `DB` 绑定执行 `0001_initial.sql` 的建表语句；表结构和 Wrangler 兼容的 `d1_migrations` 标记在同一 D1 batch 事务中提交。重复和并发初始化不会清空数据，失败则回滚并允许下次请求重试。非法 Webhook 在访问数据库前就被拒绝。

每个运行实例只缓存已完成的初始化，不跨请求共享正在执行的 D1 Promise。自动初始化只适用于已发布的、幂等的初始建表文件；未来 schema 变更需要新增迁移和升级方案，不会在请求中自动执行任意新增 SQL。已用 Wrangler 迁移的旧数据库可直接使用；运行时初始化的数据库也可继续使用 `npm run db:remote` 执行后续经审核的迁移。

登录产生 256 位随机会话标识；D1 存 SHA-256(标识 + 管理密码)，Cookie 不含密码且为 HttpOnly、SameSite Strict。HTTPS 时启用 Secure。登录受每 IP 和全局限频保护；生产只使用 Cloudflare 提供的客户端 IP 头。密码变化会使旧 Cookie 找不到对应会话。每个管理接口验证会话；写操作还需要同源 Origin（如存在）与自定义请求头，不开放跨域 CORS。

## 数据表

| 表              | 内容                                             |
| --------------- | ------------------------------------------------ |
| `users`         | Telegram 身份、验证有效期、封禁/白名单状态与冷却 |
| `events`        | 时间、方向、状态、原因、可选文本内容和处理说明   |
| `message_links` | 双向聊天与消息 ID 对应关系                       |
| `challenges`    | 一次性验证会话                                   |
| `updates`       | Webhook 去重、处理租约与失败状态                 |
| `rate_limits`   | D1 原子计数的固定窗口限频                        |
| `settings`      | 防护配置、连接信息、加密后的 Turnstile Secret    |
| `sessions`      | 后台会话摘要和过期时间                           |

统计与历史查询使用事件时间和状态索引；过滤用参数化 SQL。今天根据浏览器的当前 UTC 偏移计算自然日，默认 +08:00。跨夏令时的历史日期分组采用当前偏移，历史切换日可能存在一小时偏差；精确审计以事件时间戳为准。

清理只删除超期日志、映射、短期状态，不删除封禁用户。单次清理限制事件和映射各 2,000 条、更新/限频各 5,000 条，避免一次清理吞掉免费写入额度。大流量下仍应监控 D1 额度和积压。
